# 面试演示与追问

这是个人实验项目，支持用真实运行结果讲清方法。介绍时如实说明个人实现范围及 AI 辅助情况；没有生产部署、客户数据或线上收益证据，就不声称有。

## 三分钟演示

1. 运行 `python -m chronos_bench demo --out runs/demo`，打开 HTML，指出数据为合成、任务为小时级 rolling-origin 多步预测。
2. 看同一 horizon 的 `ridge_lags` 与 `ridge_calendar`：日历特征是否降低 MAE？是否在全部 horizon 都有效？以实际结果回答。
3. 打开 JSON 的 `splits`，手算一个 train 最后 target 与 validation 最早 origin 的关系，说明为什么要按 horizon 清除边界样本。
4. 对比区间目标覆盖与实际覆盖。指出漂移/依赖性限制，而不是把 90% 作为已经证明的性质。
5. 打开 `tests/test_protocol.py` 的未来扰动测试，展示模型选择不受测试标签影响。

## 核心追问

**为什么没用 Transformer？**

目前先解决可靠评估与强基线问题。数据量小且周期规律强，深度模型会增加成本；下一步可以复用同一 origin/target 协议接入模型，用相同划分与调参预算比较。不能凭模型名字判断效果。

**为什么 calendar 特征可以引用目标时刻，而 y 不行？**

目标日期的小时和星期在预测前已知，未来真实负荷未知。外生特征必须记录生成/发布时刻，不能只看它的事件时刻。

**测试特征里为什么有前几小时的真实值？**

本项目模拟在线逐小时滚动预测，每个预测 origin 都有新观测到达。若业务是日初一次性预测全天，需要 fixed-origin 特征构造或递归预测，不能直接复用当前结果。

**校准集为什么不能拿来继续选模型？**

那会把校准数据用于选择，残差分布会受选择影响。这里先按验证分数固定模型和参数，重训后只用校准块估计半宽。若迭代研究中反复看测试集，仍可能产生研究者层面的过拟合，代码无法单独解决。

**区间覆盖不够怎么办？**

先按时间/小时分解覆盖率与残差分布，区分漂移和条件异方差，再比较滚动校准、条件分位数、归一化残差等方案。更宽的区间也许能换来覆盖率，但应一起看 width 和 interval score。

**为什么拒绝缺失值？**

默认插值可能用到未来点；自动填补也会改变业务语义。先明确数据契约，后续把 causal imputer 放入每折训练管线，测试只能使用过去拟合的状态。

**实际投入和成果怎么写到简历？**

完成后可写：“实现多步时序预测实验平台，比较季节基线、Ridge 与梯度提升模型；设计基于 origin/target 的时间边界清除、独立残差校准、特征消融与可追溯 HTML 报告。”性能数字只能引用自己复现的指定数据与协议。不要把合成数据上的提升写成真实业务收益。
